# Development

See [README.md](README.md) for installation, commands, and the public API.
The editable install uses this checkout directly; console entry points are in
`pyproject.toml`. Reinstall with `python -m pip install -e ".[plot]"` after
changing entry points or dependencies.

## Processes and transport

Student scripts and tools connect to one local provider on loopback TCP
(default port 38475). A per-user temporary token authenticates connections.
`VSSS_PROVIDER_PORT` selects another endpoint, useful for isolated tests.
The first client starts live mode automatically if no provider is reachable.
Explicit live/bag providers remain selected until Ctrl+C.

The live provider owns UDP reception and one BLE worker per car. Local clients
share those workers; requests and acknowledgements are mapped back to their
originating sessions. The latest explicit velocity or waypoint command owns
motion. Readers do not take ownership. An owner disconnect sends stop; other
clients remain connected. BLE heartbeat/lease traffic is generated by the worker,
independently of client input sampling.

UDP and BLE events fan out to independent observers. GPS builds field state from
UDP; the observer records original datagrams and BLE operations; the plotter
uses the same observation interface. A slow observer ends with an explicit
overflow rather than silently losing data or blocking control.

## Internal Python modules

| File | Responsibility |
| --- | --- |
| `vsss/_provider.py` | Local server, authenticated client roles, discovery cache, source selection, observation fanout, startup/shutdown. |
| `vsss/_provider_connection.py` | Client handshake and automatic detached startup, including hidden Windows launch. |
| `vsss/_provider_car.py` | One shared car session: worker lifetime, client routing, motion ownership and disconnect behavior. |
| `vsss/_ble_client.py` | Synchronous BLE-facing client used by `Car`; validation, requests, readback and acknowledgement waits. |
| `vsss/_ble_worker.py` | Async Bleak connection, reconnect loop, command coalescing, heartbeats and traced GATT operations. |
| `vsss/_ble_protocol.py` | UUIDs, binary layouts, status decoding and controller parameter definitions. |
| `vsss/_provider_vision.py` | Shared UDP subscriptions, packet validation and periodic HTTP status polling/cache. |
| `vsss/_bag.py` | Streaming JSONL reader and replay timing. |
| `vsss/_bag_provider.py` | Replay source served through the provider protocol, including end-of-stream and loop handling. |
| `vsss/_runtime.py` | Implementation of the public `@run` cleanup decorator. |

`vsss/provider.py` is the common observation/discovery client.
Live and bag modes share its wire protocol. Bag mode never opens physical BLE
or UDP connections and rejects car commands. Simulation can implement the same
protocol later.

## Tools and recordings

`tools/vsss_*.py` implement the installed provider, observation, plotting and
teleop commands. Teleop quantizes inputs and sends changes only; the BLE worker
retains the active command and sends its heartbeat. Each gamepad or keyboard
layout is assigned independently.

`tools/calibrate.py` handles measurement, proposal, saving, application and
reset; `tools/_fit_trim.py` fits the correction matrix. Short calibration pulses
do not establish safe closed-loop gains, so controller gains are retained.

Other development entry points use `python -m tools.MODULE -h`:

- `run`: guarded motion/observation and configuration experiments.
- `guarded_waypoint`, `waypoint_repeat`: bounded navigation and repeated trials.
- `check_robot_ble`: firmware/BLE inspection.
- `ball_dynamics`: contact/rolling model fitting and bag analysis.
- `mpremote_no_reset`: mpremote wrapper avoiding native ESP32 USB DTR/RTS reset;
  requires `mpremote` and `pyserial`.

Generated runs belong in ignored `tools/runs/`.
Bags begin with a schema-3 `bag_header` containing the provider snapshot and
cached vision setup/health metadata. UDP entries preserve exact bytes in
`payload_base64`; BLE entries contain actual GATT operations and origin/session
information. `motion_owner` events mark takeovers. A final `session_end` reports
whether recording completed cleanly. Replay preserves original timestamps under
`replay` and supplies fresh delivery timestamps for GPS freshness checks.

## Vision server: aruco_gps

`aruco_gps/` is a separate Git repository included as a submodule. On the lab
desktop it runs independently and serves all clients on the lab network.
It captures the camera, locates the board and car markers, optionally detects
balls, and publishes field telemetry over UDP. Cars receive their own feedback
directly from that server; laptop GPS reception is a separate subscription.

- `run.sh` selects a vision setup, stops matching previous stack processes from
  that checkout, and launches `camera_stream.py --run-vision`.
- `camera_stream.py` supervises capture, the HTTP camera viewer, and `main.py`,
  which performs detection and telemetry publication.
- `vision_setup.py` defines serializable board/camera/marker/ball settings.
  A setup includes its ball detector when ball detection is wanted.
- `runtime_status.py` provides setup and health metadata through
  `http://HOST:8080/api/v1/status`. The VSSS provider polls this every five seconds
  and retains the last successful result with its age and any later error.
- `plotter2d.py` supplies the renderer reused by `vsss-plot`; portable setup
  metadata lets it reconstruct the field without server-side PNG assets.

Default telemetry is UDP 5000 with `POSE_SUBSCRIBE` / `POSE_UNSUBSCRIBE` on
UDP 5001. Server configuration and operation are documented in
[aruco_gps/README.md](aruco_gps/README.md).

The desktop can be inspected and modified remotely using SSH, either on the lab
hotspot or through Tailscale. Local connection instructions are in
[GPS_SERVER_SSH.md](GPS_SERVER_SSH.md), intentionally ignored by Git.
Changes to the local submodule do not deploy themselves: copy or update the
desktop checkout, restart the stack, and verify the status endpoint.
Commit/push submodule changes before publishing the parent repository's new
submodule reference.

## Firmware and verification

`mp/` contains the MicroPython files pre-flashed by the support team.
`main.py` wires together BLE (`ble_server.py`), Wi-Fi recovery
(`telemetry_recovery.py`), UDP poses (`pose_receiver.py`), onboard navigation
(`onboard_controller.py`), trim (`axis_trim.py`), and motors (`mecanum.py`).
`robot_config.py` / `robot_config.json` define defaults and stored configuration.
Copy support modules first, configuration next, and `main.py` last.

`navigation_log.py` records a bounded RAM ring while moving and flushes rolling
`navigation*.jsonl` files on stop/arrival/fault/disconnect. Abrupt power loss can
lose the unsaved motion trace. Stop while still powered before collecting logs.

Reusable tests live in [.tests/](.tests/README.md). They use fake BLE and synthetic
telemetry, including real subprocess checks, without moving physical cars:

```sh
python -m unittest discover -s .tests -v
```

Vision tests run from that repository's environment:

```sh
cd aruco_gps
python -m unittest discover -s tests -v
```

`blockly_python_demo/` remains an experimental integration.
